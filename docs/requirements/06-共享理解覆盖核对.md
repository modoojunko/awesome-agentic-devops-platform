## v0.6 六条定稿决策核对表（grill 对齐）

| # | 定稿决策 | 落实位置 |
|---|---|---|
| 1 | **完成统一口径**：某需求「完成」= 其全部直接子级「已完成/已交付」（本次定稿修订：需求层状态「完成」改名「开发完成」，见 v0.13 #1 标注）；中间态（子级已创建但未全完成）不叫完成——L1 叫「实施中」、L2 叫「开发中」、L3 叫「实施中」；状态与进度永远一致（显示完成即进度 100%） | RE-05、RE-06、RE-15、RE-16、§3.1.3/3.1.4 |
| 2 | **三层划分判据**：初始需求 = 业务上的描述/目标（如「提升研发效能 100%」）；产品需求 = 用什么办法解决业务问题（方案）；系统需求 = 如何去完成产品的设计（技术实现）；任务 = 最小颗粒度的交付 | [02-名词表](./02-名词表.md)、§3、RE-01 |
| 3 | **直接创建来源 + L3 生命周期**：产品经理可直接创建产品需求（自身规划类，跳过访谈澄清，但评估 + 评审仍走，PM 自行产出需求文档）；架构师/研发可直接创建系统需求（技术改进/技术债类，跳过评估/PRD/评审，可选轻量技术评审，带「技术改进，未走业务评估」标记）；L3 生命周期定为 新建→设计→评审→实施中→完成（后改名「开发完成」） | RE-01、RE-05、§3.1.1/3.2.3 |
| 4 | **评审打回 = 回上一环节**：L2 评审打回 → 回 PRD；L3 评审打回 → 回设计；打回理由作为修订指引记录在需求上（取代「回填访谈循环」机制，RV-05 相应改写）；累计 3 次打回 → 挂「强制人工」旁路标记（B4，本次定稿修订：非状态、状态机不变、AI 不代行、路由人工） | RV-04、RV-05、§3.1.5/3.2.2/3.2.3 |
| 5 | **挂起/阻塞标记不沿需求树自动传递**：标记永远是某个对象自己的；父级详情与 Dashboard 显示「下级存在 N 个阻塞/挂起」风险提醒，解除后消失 | RE-18、TA-02、DB-01、AI-08、§3.1.5 |
| 6 | **可开发判定 + 拆分质量信号**：系统需求「已拆分」= 该需求下全部计划任务均已确认创建，部分确认仍属待拆分、不进可开发列表；拆分接受率低（如 7 拆只确认 3）时系统预警「拆分质量或上游需求清晰度可能有问题」，可选重新拆分，作为 AI 拆分质量反馈指标 | RE-17、TA-05、TA-08、§3.1.5 |

| 1 | **空间模型（修正 RBAC）**：租户 = 一个公司，公司下多个空间（原「项目」= 特定需求集目的容器）；账号（公司级，可加入多空间）→ 成员（空间级，绑空间内角色）；角色在空间下定义、可自定义（如「迭代负责人」）；空间负责人维护空间内角色/权限/账户关系；租户管理员管账号、建空间、定空间负责人 | [02-名词表](./02-名词表.md)、TE-01/03/04/12/13、§3 |

| 4 | **废弃扩展为任意阶段终止态**：评估判档废弃或任意阶段（开发到一半等）直接废弃，带原因、可留痕、可恢复；父级完成判定排除废弃子级；不做但需留档 → 用挂起 | RE-18、EV-04、§3.1.5 #22、§3.5 #4 |
| 5 | **去归档**：删除「归档」概念（未拍板过的多出来功能）；RE-04 改为仅「删除（二次确认）」 | RE-04、§3.5 |
