这是「AI 辅助、人机可替换」的需求管理 SaaS 平台的产品需求文档（PRD）。文档已拆分为多文件，本文件为索引与阅读入口。

**3 句话产品简介**：把需求从想法管到上线——AI 干重活、你只做决定。一人公司/中小团队把一条需求丢进来，AI 追问澄清、写文档、评估价值、出 PRD、主持评审、拆任务，**AI agent 当员工**认领开发/测试任务；人的精力只花在关键裁决上（确认档位、评审通过、测试三方确认、验收、发布）。需求按「初始 → 产品 → 系统 → 任务（开发/测试双类型）」三层树走完流程，开发任务发布上线 + 测试任务三方确认 = 需求「开发完成」，随后经验收段（开发完成→待验收→已验收）由产品经理业务裁决 + 提出人整树确认敲定「已验收」，进度全自动汇总。

**时间有限先读**：`01` 了解产品是什么、给谁用 → `03` §3.1.1 流程图 + §3.4.2 文字走查（一条需求从提出到上线的完整例子）→ 再回 `03` §3.2 看细节。`06/07` 是决策核对与追溯用、`08` 是业务侧 DDD 划分（供架构对齐），业务阅读可略读。

## 版本历史

- **v0.13**：回填需求验收环节 grilling 决策——①**需求验收状态机**：需求状态机加验收段「…→进行中→完成→待验收→已验收」（本次定稿修订：需求层状态「完成」统一改名「开发完成」，任务层「已完成」不变）；「完成」= 开发活动彻底结束（进度 100%、状态与进度一致）；「待验收」= 完成即自动进入、通知产品经理 + 提出人并行验收（功能已上线双方都能看到）；「已验收」= 双方对齐敲定（终态）；验收段不改变进度 ②**验收不通过 → 返工重走**：产品经理打回 / 提出人异议经评估 → 需求回「进行中」返工，按流程重走再验收（本次定稿修订补执行路径：挂「返工」待办 → 人工确认拆返工任务 → 开发/测试/验收/发布 → 再回开发完成 → 再入待验收；需求级验收打回累计 3 次强制升人工，与任务级共用口径）③**待验收提醒按优先级**：进入即通知、逾期按优先级催办（P0=1天/P1=2天/P2=3天/P3=7天，映射可配置 NT-02），直到验收敲定停止（本次定稿修订补：父级回落「进行中」时提醒同步停止）④**提出人线上验收**：提出人验收他提的整棵需求（提 L1 就 L1 完成后触发、L2 就 L2，以此类推），非具体任务、后置确认不阻塞完成（本次定稿修订补：提出人整树线上验收只在其提出层执行一次，子级验收由产品经理业务裁决）。叶子功能数不变（89 项）；**本次定稿修订新增 RE-19 需求验收单、NT-04 我的待办/决策队列（89→91），其余六角色评审 grilling 定稿口径（B1~B4、M1/M4/M5/M6/M9/M10/M12）见版本索引「本次定稿修订」段**。
- **v0.12**：回填大规模 grilling 定稿决策——①**任务双类型**：开发任务 6 态 + 废弃（待处理→进行中→待测试→待验收→待发布→已完成）、测试任务 4 态（待处理→进行中→待执行→已完成，不发布不验收）；「待测试」仅属开发任务、「待执行」仅属测试任务；L3 拆分同时拆两类任务（开发任务由开发人员/架构师基于系统设计拆、测试任务由测试人员基于 UI 设计+PRD 操作流程+接口拆）②**测试环节**：测试计划/用例/报告 = 本期流程占位（不实现存储）；三方确认 = 产品经理 + 架构师 + 测试人员；测试打回累计 3 次升架构师、验收打回累计 3 次强制升人工、任何打回返工后必须重新测试；发布单只装「测试通过 + 验收通过」的开发任务；测试任务跟随需求进迭代、独立估时、分派测试角色、计入团队负载 ③**角色体系重构**：人类角色 7 类（空间负责人/产品经理/架构师/迭代负责人/开发人员/测试人员/UI设计师）；取消「评审主持人」（L2 产品经理主持、L3 架构师主持）与「验收负责人」（验收归产品经理）；Agent 目录 12 类（新增测试 Agent）；提出人为成员属性（不可见迭代/任务/成员）④**版本模型补充**：已交付=版本下所有需求已完成（系统判定；**本次定稿修订：改为「已交付 = 版本下所有需求均已『已验收』」，挂起/阻塞/进行中/开发完成/待验收 一律计未交付，验收段为交付判定必经环节**）；废弃自动移出版本/恢复不回版本；挂起留在版本；需求可不归版本（未归=backlog）；父级归版本子级跟随/移出整棵子树移出；需求按版本、任务按迭代；归版本由产品经理决定 ⑤**UI 设计**：PRD 定稿后即启动（不等评审通过），UI 设计师（必须角色）产出挂 L2、作 L3 设计输入 ⑥**改名**：「产品负责人」42 处统一改「产品经理」（人）；「产品经理 Agent」不变。叶子功能数不变（89 项）。
