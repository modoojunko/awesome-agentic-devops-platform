正在开发一个 **SaaS 需求管理平台**，核心是「AI 辅助、人机可替换」的需求全生命周期流水线。**核心用户 = 一人公司**（1 人或几个员工的完整有限公司，AI agent 当员工是核心场景）；扩展 = 中小团队。

**关键事实**（2026-08-06 PRD v0.12）：
- 三层需求树：初始需求（业务描述）→ 产品需求（方案）→ 系统需求（技术实现，按业务领域拆）→ 任务（最小交付）
- **需求层状态机（v0.10 + v0.13 验收段）**：L1 新建→澄清中→已澄清→评估中→已评估→进行中→完成→待验收→已验收；L2 新建→评估中→已评估→PRD→评审中→已通过→进行中→完成→待验收→已验收；L3 新建→设计→评审→进行中→完成→待验收→已验收；需求层无「待发布」、中间态统一「进行中」
- **验收环节（v0.13）**：完成=开发活动彻底结束（进度100%、状态与进度一致）→ 自动进「待验收」→ 产品经理+提出人并行验收（功能上线双方可见）→ 对齐敲定 →「已验收」（终态）；验收不通过 → 回「进行中」返工重走再验收；待验收提醒按优先级（P0=1天/P1=2天/P2=3天/P3=7天，可配置 NT-02）直到验收敲定；提出人验收他提的整棵需求（提 L1 就 L1 完成后触发，以此类推）、后置不阻塞完成；L3 设计定稿确认人按来源分（L2 拆的业务 L3 产品经理确认、直建技术 L3 架构师确认）
- **任务双类型（v0.12）**：
  - **开发任务 6 态 + 废弃**：待处理→进行中→待测试→待验收→待发布→已完成（=发布成功）+废弃
  - **测试任务 4 态**：待处理→进行中→待执行→已完成（执行用例+三方确认，不发布不验收）
  - 「待测试」仅属开发任务、「待执行」仅属测试任务（=用例设计完成）；任务有「类型」字段
  - L3 拆分同时拆两类（开发任务由开发人员/架构师基于系统设计拆、测试任务由测试人员基于 UI 设计+PRD 操作流程+接口拆）
  - 测试任务跟随需求进迭代（不独立排期）、独立估时（人/Agent 双轨）、继承需求优先级、分派测试角色、计入团队负载
- **测试环节（v0.12）**：技术设计定稿→测试计划→并行写用例→开发任务进「待测试」→测试任务「待执行」执行→测试报告→三方确认（产品经理+架构师+测试人员）→测试任务完成→开发任务进待验收；测试计划/用例/报告=本期流程占位（不实现存储）；测试打回累计 3 次升架构师、验收打回累计 3 次强制升人工、任何打回返工后必须重新测试；发布单只装「测试通过+验收通过」的开发任务
- **角色体系（v0.12）**：空间级人类角色 7 类（空间负责人/产品经理/架构师/迭代负责人=技术leader/开发人员分栈/测试人员/UI设计师必须）；取消「评审主持人」（L2 产品经理主持、L3 架构师主持）与「验收负责人」（验收归产品经理）；Agent 目录 12 类（含新增测试 Agent）；提出人为成员属性（可见自己需求 L1-3 状态/进度/完成，不可见迭代/任务/成员）
- **版本模型（v0.12）**：版本=规划维度，装需求（可 L1/L2/L3），需求可不归版本（未归=backlog），归版本由产品经理决定；已交付=版本下所有需求已完成（系统自动）；需求废弃→自动移出版本、恢复不回版本；挂起→留在版本；父级归版本子级跟随、移出整棵子树移出；需求按版本、任务按迭代；规划交付日期=参考
- **UI 设计（v0.12）**：PRD 定稿后即启动（不等评审通过）；UI 设计师（必须角色）产出挂 L2、作 L3 设计输入
- **改名（v0.12）**：「产品负责人」42 处统一改「产品经理」（人）；「产品经理 Agent」不变
- 其他：版本、backlog（待排期需求池）、废弃级联+恢复回最初状态、挂起/阻塞全局标记不沿树传递、评审打回=回上一环节（3 次升人工）、L1 评估（做/不做门槛，复用 EV）、缺陷管理=第二部（第一部完全不管 bug）、去归档
- 技术栈：TypeScript 前后端分离（React + NestJS + PostgreSQL + Redis + 自建 AI 流水线状态机 + Docker）
