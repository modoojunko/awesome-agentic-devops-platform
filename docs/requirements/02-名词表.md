# 02 · 业务名词表

> 属于「SaaS 需求管理平台 PRD」的一部分 · v0.13
> 本文件位置：核心概念与名词表
> 阅读顺序：前一篇 [01-产品定位](./01-产品定位.md) → 下一篇 [03-需求全生命周期流程详解](./03-需求全生命周期流程详解.md)

## 核心业务概念

| 名词 | 说明 |
|---|---|
| 租户 Tenant | 多租户隔离边界；**租户 = 一个实际公司**；租户下多账号、多空间。 |
| 账号 Account | 登录主体（公司级身份）；可加入多个租户，登录后切换租户上下文；加入某空间后成为该空间成员。 |
| 角色 Role | 系统内**权限打包的虚拟对象**，只与权限有关系，不绑定具体人（v0.9）；每个角色 = 一组权限点；分**人类角色**（空间负责人/产品经理/架构师/迭代负责人/开发人员/测试人员/UI设计师等，可自定义，v0.12 重构：取消「评审主持人」与「验收负责人」）与 **Agent 角色**（AI·产品经理/AI·架构师/AI·前端/AI·后端/AI·测试/AI·UI 等，Agent 专属，对应内置 Agent 目录 12 类，v0.12）。 |
| 成员 Member | 真实人 或 Agent 在空间内的映射（v0.9）；**成员被赋予某角色 → 获得该角色的权限**（「是什么角色决定有什么权限」）；同一个人/Agent 可在不同空间被赋予不同角色。 |
| 角色与权限 RBAC | 权限模型：**账号 → 空间成员 → 角色 → 权限**；角色在空间下定义、绑定权限集，分人类/Agent 两类；空间负责人维护空间内角色/权限/账户关系；租户管理员管账号、建空间、定空间负责人。 |
| 空间 Space | 租户下的目的容器（原「项目」）：**为同一目标服务的一堆需求被归拢到一起**；空间内含需求集、版本、迭代、成员（人 + Agent）；一个公司（租户）可有多个空间。 |
| 团队 Team | 空间下的协作建制（可选分组），成员（人 + Agent）的归属单位；承载流水线处理人模板。 |
| Agent | 平台内置的一类成员（产品经理/架构师/前端/后端/测试/UI/UX/DBA/DevOps/SRE/运营/客服，共 12 类，v0.12 新增「测试 Agent」），具备执行流水线环节的能力；作为成员被赋予 **Agent 角色** 获得对应权限。**评估环节由产品经理 Agent 承担（评估是其子能力），不单列「评估 Agent」为目录类目（本次定稿修订）**。 |
| 需求分类 RequirementType | 需求分三类：**初始需求 / 产品需求 / 系统需求**；任务为最底层执行单元（**开发任务 / 测试任务 双类型，v0.12**）。 |
| 需求树 Requirement Tree | 分解关系：初始需求 1:N 产品需求，产品需求 1:N 系统需求，系统需求 1:N 任务；父需求与子需求相互关联。 |
| 需求 Requirement | 分层载体：携带本层产物与独立的流程状态（L1 澄清/文档，L2 评估/PRD/评审，L3 设计/评审/拆分产物与任务）；**归属版本（单选，v0.9）**；需求可不归版本（未归 = 在 backlog，v0.12）；父级归版本 → 子级跟随、移出 → 整棵子树移出（v0.12）；需求废弃 → 自动移出版本、恢复废弃不回版本（v0.12）；需求挂起 → 留在版本（算未完成，v0.12）；**状态机含验收段（v0.13）：… → 进行中 → 开发完成（= 开发活动彻底结束，全部直接子级已完成，进度 100%）→ 待验收（产品经理 + 提出人并行验收）→ 已验收（双方对齐敲定，终态）；验收不通过 → 回「进行中」返工重走再验收**；验收段交互载体 = **验收单**（功能清单 / 验收项 / 上线链接 / 通过·异议 / 单内对话，B1）；「已验收」前置 = 全部直接子级均已「已验收」、真终态不可回落（B3）；支持挂起 / 阻塞全局标记、废弃（任意阶段终止态）。 |
| 开发完成 DevDone（本次定稿修订） | **需求层（L1/L2/L3）状态机的完成态**：由「进行中」经全部直接子级已完成后进入，= 开发活动彻底结束（进度 100%、状态与进度一致）；随后系统自动进入「待验收」。**与任务层「已完成」严格区分**：任务层「已完成」是任务状态（开发任务 = 发布成功、测试任务 = 执行用例 + 三方确认），需求层一律用「开发完成」、不用「已完成」；父级需求「开发完成」判定 = 全部直接子级处于「开发完成 / 待验收 / 已验收」（v0.13 验收段容差，任一直接子级挂起/进行中 → 父级不判开发完成，保持「进行中」）。 |
| 验收单 Acceptance Sheet（本次定稿修订） | 需求验收段（待验收→已验收）的**交互载体**：**挂需求详情、不新增页面**，含 **功能清单 + 验收项 + 上线链接 + 通过 / 异议动作（附原因）+ 单内对话**；异议 → 产品经理回应（接受返工 / 说明理由请撤回），留痕 = **对齐记录**；一人多角验收只执行一次（B1）。 |
| 验收子状态 AcceptSubState（本次定稿修订） | 需求落库的验收裁决字段：**pmDecision（产品经理裁决）+ proposerConfirmation（提出人确认，仅提出层）**；「已验收」守卫 = 全部直接子级均已「已验收」（真终态不可回落）；非提出层仅产品经理裁决（M2）。 |
| 强制人工 ForceManual（本次定稿修订） | **旁路标记、非状态**：评审 / 验收打回累计 3 次 → 需求挂「强制人工」标记，状态机不变（仍回原流转），该环节 AI 不代行、路由人工，人工处理通过后解除（B4）。 |
| 回退 Rollback（本次定稿修订） | **纠错动作，≠ 打回**：产品经理 / 空间负责人（权限 TE-04）可将任意需求 / 任务强制回退到指定合法前置态，必填原因留痕；回退不计打回计数、不触发升人工（M10）。**常规纠错回退仅作用于非终态——需求「已验收」、任务「已完成」不可用常规回退；终态误设由空间负责人走独立「数据修正」（高权限 + 二次确认 + 留痕，不属常规回退）**。 |
| 待办 / 决策队列 ToDo·DecisionQueue（本次定稿修订） | 「我的待办」按角色聚合「需要我处理」的项：待确认档位 / 待评审裁决 / 待三方确认 / 待验收（裁决 / 整树确认）/ 返工待办 / 异议回应；对象级待办、不进复杂队列引擎（NT-04，M0）。 |
| 废弃恢复（快照回滚）RestoreSnapshot（本次定稿修订） | 废弃恢复 = **整棵子树回滚至废弃前状态快照**（原 v0.8「回最初状态」口径废止）；已废弃子级保持废弃可单独恢复、已完成任务保持已完成；留痕「已恢复(回滚至废弃前)」（M6）。 |
| 版本 Version | **规划维度**（v0.9，v0.12 补交付判定）：回答「这一版交付哪些需求」；需求**归入版本（单选）**，带规划交付日期；**版本「已交付」= 版本下所有需求均已「已验收」（系统自动判定；本次定稿修订：原 v0.12 口径「所有需求已完成」改为「所有需求均已已验收」，挂起/阻塞/进行中/开发完成/待验收 一律计未交付，验收段为交付判定必经环节）**；需求废弃 → 自动移出版本、恢复不回版本；需求挂起 → 留在版本（算未完成）；版本页聚合显示该版本下所有需求及各自进度；**与迭代无直接绑定关系**（数据上可由 版本→需求→任务→迭代 推导）。 |
| backlog（待排期需求池） | **已确认但尚未排期的需求（L2/L3）+ 未归版本的需求（v0.12）+ 任务（开发/测试）**的集合（v0.11 定名，v0.12 补：需求未归版本即在此）；业务上是「池子」、实现上是一个筛选视图（把未排期的需求和任务筛出来，可按优先级/档位/可开发状态筛选）；AI 自动装填（IT-06）与手动拖入迭代（IT-05）的候选来源；挂起的任务移出迭代池后回到这里等待重新排期。 |
| 就绪度 Readiness | 系统需求「已拆分」= 其下**全部计划任务（开发 + 测试，v0.12）已确认创建**；部分确认仍属待拆分；已拆分系统需求 = 可开发（RE-17），可进入迭代装填候选。 |
| 优先级 Priority | 需求的业务优先级（P0/P1/P2/P3，可选）；与价值评估是两个维度——**L1 评估判定「这个业务目标值不值得做」（做/不做门槛）**、**L2 评估判定「方案价值档位 S/M/L/废弃」**（两套语义，v0.10），优先级决定「先做哪个」；**也决定待验收提醒频率（P0=1天/P1=2天/P2=3天/P3=7天，v0.13）**。 |
| 进度汇总 Progress | 进度由系统自动汇总展示；**某需求显示「开发完成」即其全部直接子级已完成（开发任务 = 发布成功、测试任务 = 执行用例 + 三方确认，v0.12）、进度为 100%，状态与进度永远一致**；**需求验收段（开发完成 → 待验收 → 已验收）不改变进度，进入待验收时进度即 100%（v0.13）**。 |
| 全局标记 Marker | 挂起 / 阻塞：任意需求/任务、任意状态可打、带原因、解除回原状态；挂起 = 自选搁置，阻塞 = 被外部依赖/条件卡住；**标记不沿需求树自动传递**，但父级详情与 Dashboard 显示「下级存在 N 个阻塞/挂起」风险提醒。 |
| 任务 Task | 可独立交付的最小颗粒度交付单元，含**类型（开发任务 / 测试任务，v0.12）**、负责人、估时（双轨）、依赖、看板状态；**开发任务状态机（6 态 + 废弃）= 待处理 → 进行中 → 待测试 → 待验收 → 待发布 → 已完成 + 废弃**（「已完成」= 发布成功；验收不通过打回「进行中」）；**测试任务状态机（4 态）= 待处理 → 进行中 → 待执行 → 已完成**（执行用例 + 三方确认后完成，不发布、不验收）；「待测试」仅属开发任务（等测试验证）、「待执行」仅属测试任务（测试用例设计完成 = ready）。 |
| 发布单 Release | **属于迭代**（v0.8）的发布批次容器：一个迭代内可建多个发布单，每单装一批「待发布」任务，随做随发；发布单随 CI/CD 发布，**成功后发布单关闭 → 范围内任务自动置「已完成」**。**需求不进发布单**——需求「完成」由系统按「其下全部开发任务已完成（发布成功）+ 测试任务已完成（三方确认）」自动判定。**已装入发布单的任务被挂起/废弃 → 自动移出发布单；发布单发布时只发「仍为待发布」的任务（v0.10）**；**发布前置（v0.12）：发布单只装「测试通过 + 验收通过」的开发任务（开发任务处于「待发布」即隐含前置已满足）；测试任务不进发布单**。 |
| 迭代 Iteration | 排期单元（执行维度，v0.9），装任务（开发/测试任务均随需求进迭代，测试任务不独立排期，v0.12）、自带看板 + 甘特图 + 负载图；迭代内可多次发布（多个发布单）；**迭代不挂版本**（与版本无直接绑定）；**需求按版本、任务按迭代**。 |
| 看板 Kanban | 任务看板按类型分列（v0.12）：开发任务 6 态列 = 待处理 → 进行中 → 待测试 → 待验收 → 待发布 → 已完成 + 废弃；测试任务 4 态列 = 待处理 → 进行中 → 待执行 → 已完成；**可按类型筛选**；挂起 / 阻塞为全局标记（不占列）。 |
| 处理人 Handler | 流水线某环节的承担者：人 / Agent / 人机协作 三选一。 |
| 容量 Capacity | 成员可并行承接的任务数上限（开发/测试任务均计入，v0.12）。 |
| 估时双轨 Estimate | 同一任务的估时随认领者类型切换：人认领 → 人工工时；Agent 认领 → Agent 工时（开发/测试任务均适用，v0.12）。 |
| 评估框架 EvalFramework | 价值评估的配置化模型（维度/权重/分档阈值），S/M/L/废弃 四档。 |

## 三层需求划分判据（v0.6 定稿）

| 层 | 名称 | 含义 | 举例 |
|---|---|---|---|
| L1 | 初始需求 | 业务上的描述 / 目标 | 「提升研发效能 100%」 |
| L2 | 产品需求 | 用什么办法解决业务问题（方案） | 「引入自动化需求管理流程」 |
| L3 | 系统需求 | 如何去完成产品的设计（技术实现）；**按业务领域拆分（高内聚低耦合，一个 L3 = 一个业务领域，DDD 限界上下文落地，v0.10）** | 「工单领域」「智能分类领域」「分类报表领域」 |
| — | 任务 | 最小颗粒度的交付 | 「实现状态流转接口」 |

## 需求分层分解与环节分布（v0.6 定义，v0.10 更新状态机：去需求层待发布、中间态统一进行中、L1 新增评估，v0.13 补验收段：开发完成 → 待验收 → 已验收；本次定稿修订：需求层状态「完成」改名为「开发完成」，任务层「已完成」不变）

```
L1 初始需求：新建 → 澄清中（AI grill 访谈）→ 已澄清（产出需求文档）→ 评估中（评估业务目标「值不值得做」→ 做 / 不做（废弃））→ 已评估 → 进行中（分解为产品需求）→ 开发完成（全部直接产品需求已完成 = 开发活动彻底结束）→ 待验收（产品经理 + 提出人并行验收）→ 已验收（对齐敲定，v0.13）
L2 产品需求：新建 → 评估中（RICE 变体，S/M/L/废弃）→ 已评估 → PRD → 评审中（AI 质询、人裁决）→ 已通过 → 进行中（分解为系统需求）→ 开发完成（全部直接系统需求已完成 = 开发活动彻底结束）→ 待验收（产品经理 + 提出人并行验收）→ 已验收（对齐敲定，v0.13）
L3 系统需求：新建 → 设计 → 评审（技术评审）→ 进行中（拆分任务并执行）→ 开发完成（全部任务已完成 = 开发活动彻底结束）→ 待验收（产品经理 + 提出人并行验收）→ 已验收（对齐敲定，v0.13）；L3 按业务领域拆分（一个 L3 = 一个业务领域，v0.10）
开发任务：待处理 → 进行中 → 待测试（等测试验证）→ 待验收 → 待发布（测试通过 + 验收通过后、发布前）→ 已完成（= 发布成功）+ 废弃（终止态）；验收不通过打回「进行中」+ 必填反馈，**任何打回 → 返工 → 必须重新测试（v0.12）**；测试打回累计 3 次上升架构师裁决、验收打回累计 3 次挂「强制人工」旁路标记（状态机不变、AI 不代行、路由人工，产品经理/空间负责人介入，处理通过后解除；B4，本次定稿修订）（v0.12）
测试任务：待处理 → 进行中 → 待执行（测试用例设计完成 = ready）→ 已完成（执行用例 + 三方确认，不发布、不验收）（v0.12）；需求废弃 → 未完成测试任务级联废弃（已完成测试报告保留）
测试环节（v0.12）：技术设计定稿 → 测试人员了解设计 → 输出测试计划 → 开发进行中并行写测试用例 → 开发任务进「待测试」→ 测试任务「待执行」执行用例 → 输出测试报告 → 三方确认（产品经理 + 架构师 + 测试人员）→ 测试任务「已完成」→ 开发任务进「待验收」；测试计划/用例/报告 = 本期流程占位（概念存在，不实现存储）
发布单（v0.8，v0.10 补，v0.12 补发布前置）：属于迭代；一个迭代内可建多个发布单，每单装一批「待发布」开发任务；发布单随 CI/CD 发布，成功后关闭 → 范围内开发任务自动「已完成」；需求本身不进单（完成由系统按全部任务已完成自动判定）；**已装入的任务被挂起/废弃 → 自动移出发布单，发布时只发「仍为待发布」的任务（v0.10）**；**只装「测试通过 + 验收通过」的开发任务（v0.12），测试任务不进发布单**
完成口径：需求完成 = 其下全部任务「已完成」（开发任务 = 发布成功、测试任务 = 执行用例 + 三方确认，v0.12），系统自动判定（v0.8）；需求层无「待发布」中间态（v0.10），全部直接子级已完成即由系统直接置「开发完成」（= 开发活动彻底结束）；「开发完成」后自动进入「待验收」→「已验收」（验收段，v0.13，不改变进度）
废弃（v0.8，本次定稿修订：恢复改快照回滚）：需求废弃 → 其下未完成任务**级联废弃**；任务废弃 = 第 6 态终止（带原因、移出迭代池、不计进度分母）；废弃恢复 → **回废弃前状态快照**（整棵子树回滚；已废弃子级保持废弃可单独恢复、已完成任务保持已完成；留痕「已恢复(回滚至废弃前)」，M6）
评审打回：L2 打回 → 回 PRD；L3 打回 → 回设计（打回理由作为修订指引）
直接创建：产品经理可直接建产品需求（跳过澄清与 L1 评估，L2 评估 + 评审仍走，PM 自行产出需求文档）；
          架构师/研发可直接建系统需求（技术改进/技术债类，跳过评估/PRD/评审，但 L3 的设计 → 技术评审必走（可轻量，v0.11），带「技术改进，未走业务评估」标记）
评估两套语义（v0.10）：L1 评估 = 业务目标「值不值得做」（做/不做门槛）；L2 评估 = 方案价值 S/M/L 档位（优先级）；两者是不同环节、不同判定
废弃（任意阶段终止态，v0.7）：评估判档 = 废弃，或开发到一半砍掉 → 直接废弃（带原因、可留痕）；父级完成判定排除废弃子级；不做但留档 → 用挂起
UI 设计：PRD 定稿后即启动 UI 设计（不等评审通过，v0.12）；UI 设计师（必须角色）产出 UI 设计稿/交互原型（挂 L2）；作为 L3 设计输入（含测试任务拆分依据之一）
规模自适应：中小需求可跳过 L1，直接创建产品需求 / 系统需求
```

## 人机可替换规则

- 每个环节配置「处理人」= 人 / Agent / 人机协作。
- 配置来源优先级：**单需求覆盖 > 团队级模板 > 全局默认**。
- Agent 默认执行模式 =「草稿 + 确认」，可对 需求/团队/环节 开启全自动。
