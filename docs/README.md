## 2. 领域划分整合（PM 业务域 ↔ DDD 有界上下文）

两份文档由 PM 与架构师**并行**产出，域划分基本一致，仅两处拆解粒度不同，已对齐如下：

| PM 业务域 | DDD 有界上下文 | 对齐说明 |
|---|---|---|
| 租户与团队域（含空间） | 租户·空间与成员 | 1:1（v0.7 空间模型：租户=公司 → 空间 → 需求/迭代/成员；账号→成员→空间角色 RBAC） |
| 需求域 | **需求流水线·需求树** + **访谈** + **PRD** | v0.4 升级为「需求分层分解树」（初始/产品/系统三层 + 任务）：访谈服务 L1 初始需求层，评估/PRD/评审服务 L2 产品需求层，拆分/迭代服务 L3 系统需求层；每层独立状态机，进度向上汇总。**v0.9/v0.12 版本规划（VE-01/02）与 v0.13 需求验收段（完成→待验收→已验收）均落「需求流水线·需求树」**；v0.12 UI 设计（挂 L2）落「PRD」；RE-08~11 属「访谈」、RE-12/13 属「PRD」、其余 RE 属「需求流水线」（详见 [08](./requirements/08-DDD领域划分与限界上下文.md)） |
| 评估域 | 价值评估 | 1:1 |
| 评审域 | 评审 | 1:1 |
| 任务域 | 任务（**核心域**，价值判据） | 1:1；**v0.12 任务双类型 = 任务上下文内分「开发任务子域 / 测试任务子域」**（共享任务对象/看板/迭代/估时/分派机制）；**测试环节（计划/用例/报告占位 + 三方确认 + 测试打回）并入任务上下文**，不独立上下文；**任务工程按价值高低判为核心子领域**（「AI agent 当员工」直接载体：AI 拆分 + 双类型 + agent 认领执行 + 估时双轨），DDDUP 重做修正旧版判支撑（见 [08](./requirements/08-DDD领域划分与限界上下文.md) §1.3/§2.2） |
| 迭代排期域 | 迭代排期与发布（含看板/甘特/负载读模型 + `Release` 发布聚合，v0.7） | 1:1；**v0.12 发布单前置（只装「测试通过+验收通过」开发任务）、v0.10 挂起/废弃自动移出、v0.11 backlog（待排期需求池）作为本上下文排期候选读模型** |
| 人力分派域 | 人力分派 | 1:1 |
| AI 运行时域 | **AI Agent 运行时** + **工作流状态机** | PM 把状态机/确认策略归入 AI 运行时域；架构师拆出通用「工作流状态机」上下文（引擎通用 + 确认策略核心），供需求/任务/迭代跨上下文复用。**AI 能力定位（v0.13 明确，见 [08](./requirements/08-DDD领域划分与限界上下文.md) §1.2）：Agent 运行时 = 支撑域（通用执行载体，不承载业务决策）；工作流确认策略 = 核心域（「人机可替换」安全边界）**；AI-01~04/07/09 落运行时、AI-05/06/08 落工作流状态机 |
| 通知域 | 通知 | 1:1 |
| Dashboard/报表域 | Dashboard/报表 | 1:1 |
| 运营客服域 | 运营与客服 | 1:1 |

**核心域（差异化所在，按价值高低判据）**：需求分层分解树与流水线编排、需求分解与进度汇总规则、访谈、价值评估、评审、**任务工程**（AI 拆分 + 开发/测试双类型 + agent 认领执行 + 估时双轨）、人力分派、工作流**确认策略**（=「人机可替换」安全边界）。**通用域**：通知、状态机引擎（基础设施）、身份认证要素。**支撑域**：租户·空间与成员、PRD（含 UI 设计）、迭代排期与发布、**AI Agent 运行时**（通用执行载体，不承载业务决策）、Dashboard/报表、运营与客服（AI 能力定位见 [08](./requirements/08-DDD领域划分与限界上下文.md) §1.2/§1.3）。
